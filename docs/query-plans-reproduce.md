# Самостоятельный повтор исторического исследования SQL

Это перенос уже выполненного исследовательского измерителя, не новая функция
OrderFlow. Сохранены SELECT из зафиксированного коммита
`25ad49ca74f565a1b8a00c6dcc304bcdfd92e468`, до maintenance. Они не подменяют
SQL текущей версии приложения. Скрипт не импортирует OrderFlow или локальный снимок.

Состав: `scripts/query_plans.py` (генератор и измеритель), `resources/schema.sql`
(исторические три таблицы), `resources/queries.json` (сохранённые PREPARE/EXECUTE
и значения параметров). Нужны Python 3.12+, SQLAlchemy 2.x, psycopg 3.x — те же
зависимости, что использует OrderFlow. Ничего не скачивается автоматически.

## Подключение и границы

Задайте `ORDERFLOW_QUERY_DATABASE_URL` в окружении своего терминала. Строка
подключения не передаётся аргументом команды и не сохраняется в результатах.
Разрешён PostgreSQL через psycopg, адрес loopback (например127.0.0.1 или::1)
либо localhost, разрешающийся только в loopback; имя базы должно оканчиваться
на `_test`. Все query-параметры URL запрещены, чтобы host/service/options
не переопределяли проверенное подключение. При наличии PGHOSTADDR, PGSERVICE,
PGSERVICEFILE или PGOPTIONS в окружении скрипт также отказывается до подключения
с кодом database_environment: эти настройки могут обходить явные параметры URL.
Скрипт не удаляет и не меняет пользовательские переменные окружения. База должна быть заранее создана,
а роль — иметь право создавать в ней собственную схему. Не используйте рабочую БД.

Скрипт создаёт только случайную `test_UUID`, устанавливает собственный search_path,
помечает схему случайным маркером. Перед удалением проверяются имя, владелец и
маркер. Очистка выполняется в finally, после неё проверяется отсутствие схемы.
При потере сервера, неопределённом результате COMMIT, принудительном завершении
процесса или отказе проверки владельца
автоматическая очистка не гарантируется: исследование не объявляется успешным;
имя/маркер собственной схемы остаются в state.json для контролируемой диагностики.
DDL скрипта ограничен собственной схемой; cleanup_scope=owned_schema описывает
область очистки, а не измерение состояния public. Произвольное имя схемы из CLI
не принимается.

## Малый проверочный запуск

Из корня проекта после настройки переменной окружения:

```bash
python scripts/query_plans.py --output artifacts/query-small --rows 1000 --repeats 3 --comparison all
```

Каждый выходной каталог должен быть **новым** внутри artifacts этого проекта.
Существующий каталог, выход через `..`, ссылки и junction отклоняются. Повтор
с тем же именем не перезаписывает свидетельства; выберите другое имя.
Только для тестов предусмотрен `--test-output`: явно абсолютный существующий
пустой каталог с именем `test_query_plans_*`. В нём также нет перезаписи файлов.

Коды:0 — сравнения завершены и схема очищена;2 — параметры, подключение,
измерение или очистка не завершены;130 — прерывание пользователем. Диагностика
фиксированная, без исходных исключений, URL и локальных путей. Частичные артефакты
не считаются завершённым опытом: проверяйте код0 и cleanup.json с removed=true.

## Полный исторический размер

```bash
python scripts/query_plans.py --output artifacts/query-30000 --rows 30000 --repeats 3 --seed 20261102 --comparison all
```

При исходном seed и размере:300 позиций,30000 броней,59894 строки состава;
80% броней завершены. Алгоритм генерации сохранён. Hash массива
`[bookings, items]`, сериализованного прежним способом, должен быть:

`db82e9fc37081b25f5aab52b7a4ff28c02e9f8a0ddfb0aafdf28b69bef998d6f`.

Он включает порядок строк и значения datetime. Время симуляции фиксировано:
2030-01-01T08:00:00Z. Для меньшего rows доли округляются вниз, остаток относится
к checked_out; фактические количества сохранены в dataset.json. Размер ограничен
10..30000, число измерений после прогрева —1..5. Генератор здесь намеренно хранит
ограниченный набор в памяти, это не потоковый загрузчик больших рабочих журналов.

## Режимы и доказательства

`--comparison prepared`: исходные индексы; индекс состава с INCLUDE(quantity);
он же плюс partial checked_out; он же плюс полный bookings(status,id).
Дополнительные partial и status одновременно не присутствуют.

`--comparison portable`: отдельно INCLUDE и обычный
booking_items(product_id,booking_id,quantity). `all` выполняет обе последовательности.
В каждой точке принудительно проверяются custom (с учётом значений параметров)
и generic (общий) планы. Счётчики pg_prepared_statements подтверждают фактический
режим. Автоматическая подготовка драйвера отключена, подготовкой управляет измеритель;
это не замер автоматического выбора планов через пул HTTP-приложения.

Перед сравнением — VACUUM ANALYZE своей схемы; для каждого SELECT один прогрев
EXPLAIN и указанное число измерений. Сохраняются все JSON-планы, времена, обращения
к буферам, размер индексов, полные сортированные мультимножества результатов и SHA256.
Порядок строк без ORDER BY не сравнивается, дубликаты сохраняются. Любое несовпадение
результатов останавливает опыт. Пустые малые выборки тоже сравниваются, но они
не заменяют полный набор. Медианы пересчитываются из сырых Execution Time.

Время не обязано повторить прежние миллисекунды: кэш прогрет, фоновые процессы
не отключаются, их нагрузка не контролируется. Python3.12.14/PG17.11 были исходной
средой; фактические версии сохраняются. Это серверное время EXPLAIN, не задержка
production/API. Стоимость записи, WAL, блокировки и холодный диск не измеряются.
Индексы созданы только в испытательной схеме, в продукт автоматически не внедряются.

## Локальные проверки

```bash
python -m unittest discover -s tests -p test_guards.py -v
```

Эти тесты проверяют отказы небезопасных URL и выходов без обращения к серверу.
Независимые проверки генератора и настоящего PostgreSQL описываются в итоговом
статусе при приёмке; их нельзя заменять одним прохождением guard-тестов.
