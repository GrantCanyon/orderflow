# Запуск и эксплуатационные границы

## Обычный режим

Демо запускается только явно через `orderflow demo` или `ORDERFLOW_DEMO=1`. Команда `orderflow serve` без настроенных ключей и без деморежима отказывается запускать приложение.

Пример PowerShell — значения ключей ниже нужно заменить собственными случайными секретами:

```powershell
$env:ORDERFLOW_DATABASE_URL = 'postgresql+psycopg://orderflow:password@localhost:5432/orderflow'
$env:ORDERFLOW_API_KEYS = '{"replace-with-random-admin-key":{"id":"admin-01","name":"Администратор","role":"admin"},"replace-with-random-operator-key":{"id":"operator-01","name":"Оператор","role":"operator"}}'
orderflow init
orderflow serve --host 127.0.0.1 --port 8000
```

Ключи не сохраняются в проекте. `id` обязателен и содержит 1–80 латинских букв, цифр или символов `_.:-`; первый символ — буква или цифра. Используйте разные ID для разных людей, даже если их имена совпадают. При смене ключа или отображаемого имени сохраняйте ID. Аудит хранит этот ID и снимок имени на момент операции.

Сервер создаёт отсутствующие таблицы, но **не мигрирует существующую схему**. До публикации релизов с изменением полей нужна система миграций и проверка восстановления. Для новой учебной версии используйте новый файл SQLite или новую базу PostgreSQL; не удаляйте исходные данные ради обхода несовместимости.

## Docker с PostgreSQL

`compose.yaml` — локальное учебное окружение. Оно публикует интерфейс только на `127.0.0.1:8000`; база доступна внутри сети контейнеров. Демо содержит общеизвестные учебные ключи и не предназначено для внешнего доступа.

```powershell
$env:POSTGRES_PASSWORD = 'replace-with-a-long-random-alphanumeric-value'
docker compose up --build
```

Для этого примера пароль должен состоять из латинских букв и цифр: он вставляется в URL соединения. В иных конфигурациях специальные символы пароля необходимо кодировать для URL.

Данные PostgreSQL хранятся в именованном томе. `docker compose down` останавливает окружение, сохраняя том. Флаг `-v` удаляет данные и не нужен для обычной остановки.

Dockerfile запускает приложение от непривилегированного пользователя. Образы и зависимости должны регулярно обновляться и проверяться; контейнер сам по себе не делает сервис готовым к открытому интернету.

## Проверки и CI

Workflow `.github/workflows/ci.yml` выполняет весь набор в двух вариантах: временные SQLite-файлы и PostgreSQL 17. Для каждого PostgreSQL-теста создаётся схема `test_<uuid>`; в завершении удаляется только она. Тесты не выполняют `drop_all` для таблиц приложения.

Локально PostgreSQL проверен на версии 17.11. GitHub Actions использует служебную тестовую учётную запись внутри временного runner. Эти данные не являются секретами пользователя и не применяются в обычном окружении.

Ruff проверяет и форматирование, и ошибки кода. Браузерный сценарий дополнительно проверяет реальную связь UI с API; синтаксическая проверка JavaScript не заменяет его.

## Перед реальным развёртыванием

В текущей версии отсутствуют готовые решения следующих задач:

- HTTPS и управление доступом на внешней границе, ограничение частоты запросов и ротация секретов.
- Миграции, резервное копирование и регулярное восстановление базы.
- Метрики, оповещения, журнал неуспешной авторизации и нагрузочная проверка.
- Разделение организаций и индивидуальные права на отдельные бронирования.
- Индексы и оптимизация запросов под измеренный объём данных: текущая шкала делает запросы по позициям, а список броней загружает связанные данные отдельно.

Аудит защищён от изменения средствами приложения, но не от администратора БД. API-ключи дают доступ в общей рабочей области; они не заменяют полноценную систему пользователей. Ключ браузера исчезает при перезагрузке вкладки.

## Завершение истёкших резервов

Для корректного остатка планировщик не требуется: все запросы исключают истёкшие holds по времени. Администратор может вызвать `POST /api/admin/expire` или кнопку в журнале. Это материализует `expired` и событие аудита; повторный запуск безопасен и возвращает ноль при отсутствии новых истёкших резервов.

## Проверка контейнерной поставки

Отдельное задание `compose-smoke` в CI собирает Dockerfile, запускает Compose, ожидает доступность приложения и выполняет `scripts/smoke_http.py`: интерфейс и локальные ресурсы, учебный каталог, запрет записи наблюдателю и отсутствие новой брони. После проверки временное окружение runner удаляется независимо от результата. Этот шаг не дублируется в матрице баз.

На локальном компьютере Docker отсутствует; локально прошёл сам HTTP-сценарий против учебного сервера. Проверенная удалённая сборка базовой версии — [запуск 41362557242](https://github.com/GrantCanyon/orderflow/actions/runs/41362557242), две базы на Linux. Контейнерный шаг версии `5171082` [успешно прошёл в запуске 41363574229](https://github.com/GrantCanyon/orderflow/actions/runs/41363574229), вместе с обеими базами. Эта проверка не распространяется автоматически на последующие изменения.

## Испытания надёжности

`ORDERFLOW_LOCK_TIMEOUT_MS` ограничивает ожидание отдельной блокировки, а `ORDERFLOW_LOAD_DATABASE_URL` явно выбирает тестовый PostgreSQL для локального HTTP-стенда. Переменная испытания не заменяет рабочий `ORDERFLOW_DATABASE_URL`. Права на схемы, безопасная очистка, коды ошибок, сырые измерения и границы гарантий описаны в [руководстве по надёжности](reliability.md).

## Явное обновление индекса существующей базы

Новая база получает `ix_booking_items_product_booking_quantity` вместе с таблицей `booking_items`. Он покрывает `(product_id, booking_id, quantity)` для поиска занятости одного вида оборудования; прежний первичный ключ начинается с `booking_id`. Добавлен только этот индекс, без индекса по статусу.

Обычные `serve`, `demo`, `init` и запуск API не строят отсутствующий индекс на уже существующей таблице. Для ранее созданной базы выполните отдельно:

```console
orderflow create-indexes --database sqlite:///orderflow.db
```

Для PostgreSQL можно предварительно задать существующий `ORDERFLOW_DATABASE_URL` и вызвать `orderflow create-indexes`, не помещая URL с паролем в аргументы команды. Таблицы и данные не пересоздаются, повтор команды сохраняет записи и аудит. Команда ожидает уже инициализированную схему; это не замена `orderflow init`.

Используется обычный `CREATE INDEX`, а не `CREATE INDEX CONCURRENTLY`. На PostgreSQL операция может блокировать записи; на SQLite требуется блокировка записи. Запускайте её в согласованное окно обслуживания после резервного копирования своей базы. `ORDERFLOW_LOCK_TIMEOUT_MS` ограничивает ожидание отдельной блокировки (по умолчанию 2000 мс), но не время построения индекса после её получения. При конфликте команда завершится с кодом 1 и безопасным русским сообщением; после снятия блокировки её можно повторить. Автоматических повторов и фонового DDL нет. Одновременно несколько команд обновления не запускайте.

Проверка существования ориентируется на имя индекса. Если администратор вручную создал под этим именем иной индекс, команда его не заменяет: сначала необходимо проверить фактическое определение. Это небольшое явное обновление, а не универсальная система миграций схемы.
