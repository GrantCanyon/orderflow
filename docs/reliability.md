# Надёжность и воспроизводимое HTTP-испытание

## Что происходит при отказе

Создание брони записывает `bookings`, `booking_items`, `idempotency` и `audit` в одной транзакции. Тесты искусственно вызывают реальную ошибку SQL после каждой из этих четырёх записей, до фиксации. Независимое соединение затем проверяет, что не осталось ни одной новой строки и доступность не изменилась. После снятия тестового отказа тот же ключ успешно создаёт бронь.

Точки отказа находятся **только в тестах**, в обработчиках событий SQLAlchemy. В приложении нет специальных HTTP-заголовков, переменных окружения или скрытых маршрутов для вызова отказа.

Отдельный тест использует настоящий Uvicorn и временный HTTP-прокси на loopback. Прокси получает полный успешный ответ сервера после commit, но разрывает клиентское соединение до отправки заголовков. Повтор с тем же пользователем, ключом и телом возвращает исходную бронь; изменённое тело получает `409`. В базе остаются одна бронь, один ключ и одно событие создания.

Это проверка выбранных отказов транзакции и сети. Отключение питания, повреждение диска и восстановление из резервной копии не испытывались.

## Ограниченное ожидание блокировки

`ORDERFLOW_LOCK_TIMEOUT_MS` задаёт от **50 до 30000 мс**, по умолчанию **2000 мс**. Внутренний конструктор принимает тот же параметр: `Database(url, lock_timeout_ms=2000)`.

- PostgreSQL получает `set_config('lock_timeout', значение, true)` с параметрами, в текущей транзакции. Значение не вставляется в SQL строковой подстановкой.
- SQLite использует соответствующее ожидание занятой базы при подключении; записывающие операции по-прежнему начинают `BEGIN IMMEDIATE`.

Это предел ожидания **отдельной блокировки**, а не крайний срок HTTP-запроса. Ожидание соединения в пуле, несколько блокировок и выполнение запросов могут суммироваться. Сервис не заявляет общий двухсекундный предел ответа.

```powershell
$env:ORDERFLOW_LOCK_TIMEOUT_MS = '2000'
orderflow serve
```

## Ошибки хранилища

| Причина | HTTP / код | Повтор |
|---|---|---|
| PostgreSQL `55P03`, SQLite `BUSY/LOCKED`, ожидание соединения в пуле | `503 storage_busy` | `details.retryable: true`, `Retry-After: 1` |
| PostgreSQL `40P01` — взаимная блокировка | `503 transaction_retry` | Те же признаки повтора |
| Соединение признано недействительным или SQLSTATE класса `08` | `503 storage_unavailable` | Те же признаки повтора |
| Другая необработанная ошибка хранилища | `500 storage_error` | `details.retryable: false` |

Известные бизнес-конфликты артикула и ключа обрабатываются отдельно, как прежде. Не любой `OperationalError` объявляется блокировкой: тип определяется по точному коду драйвера. Проверки реальной занятой строки PostgreSQL и `BEGIN IMMEDIATE` SQLite подтверждают `503`, ограниченное ожидание, отсутствие частичной записи и успешный повтор после освобождения блокировки.

Публичный ответ содержит русский текст и безопасный код, без SQL, параметров, URL подключения или ключей. Обработанные ошибки не печатаются целым библиотечным traceback. Дополнительные проверки классификации используют реальные объекты исключений драйвера; это не выдаётся за физическое отключение сервера БД.

Внутри транзакции нет автоматических повторов. При потере связи во время commit нельзя обещать, что операция откатилась: результат может быть неизвестен клиенту. Поэтому сообщение предлагает повторить **создание с тем же ключом**, а не создать новый запрос. `retryable` — подсказка клиенту, не гарантия будущего успеха.

## Дополнительные границы ввода

Числовые `product_id` и `before_id` ограничены диапазоном **1…2147483647** на границах API и сервиса. Это соответствует текущим `INTEGER`-идентификаторам PostgreSQL. Значение выше границы, ноль, отрицательное число или логическое значение отклоняется до SQL. Допустимый, но отсутствующий ID возвращает `404`; допустимый курсор аудита может вернуть пустую выборку. Количества и параметры пагинации имеют собственные прежние ограничения.

Текстовые поля и отображаемые имена пользователей не допускают NUL и одиночные суррогаты Unicode. Это устраняет расхождения SQLite и PostgreSQL, не запрещая обычную кириллицу и переводы строк.

## Запуск стенда

Нужны зависимости разработки из README. Стенд поднимает временный Uvicorn только на `127.0.0.1`, использует настоящий HTTP, постоянные соединения клиентов и прогрев `GET /health` перед каждой фазой. Системный HTTP-прокси отключён для этих локальных клиентов.

```console
python scripts/load_probe.py --workers 8 --requests 200 --repeats 3 --seed 42 --mode both --output artifacts/my-load-run
```

Папка `--output` должна быть новой и находиться внутри проекта. По умолчанию создаётся уникальная папка в `artifacts/`. Внешний произвольный путь не принимается.

Без дополнительной настройки используется отдельный SQLite-файл на каждое испытание. Для PostgreSQL явно задайте URL **тестовой** базы:

```powershell
$env:ORDERFLOW_LOAD_DATABASE_URL = 'postgresql+psycopg://user:password@localhost:5432/orderflow_test'
python scripts/load_probe.py --workers 8 --requests 200 --repeats 3 --seed 42 --mode both --output artifacts/my-pg-load-run
```

Внешние SQLite-URL не принимаются: это исключает случайное испытание существующего файла. В PostgreSQL создаётся собственная случайная схема `test_<uuid>`, и отображение схемы применяется **до** создания таблиц и запуска приложения. Имя схемы не читается из окружения. При завершении проверяются формат имени и текущий владелец; удаляется только созданная схема. `public` не очищается и не используется для таблиц испытания. Пользователю БД нужны права создания схем.

SQLite-файлы остаются в папке результатов для изучения. PostgreSQL-схемы удаляются при нормальном завершении и обработанных исключениях. Принудительное завершение процесса операционной системой может оставить схему; автоматической массовой очистки чужих или старых схем нет.

## Что именно измеряется

Сценарий `shared` направляет клиентов в один общий пул. В `independent` каждому клиенту принадлежит отдельный пул. Общая вместимость и число исходных запросов одинаковы; все брони имеют один общий часовой интервал и количество 1. Часть запросов ожидаемо получает конфликт вместимости. После исходной фазы выполняются намеренные повторы успешных ключей — до 20% от количества исходных запросов.

Параметры: 1–32 клиента, от числа клиентов до 5000 исходных запросов, 1–10 повторов. Один и тот же `seed` задаёт повторяемый порядок запросов. Он не делает межпоточное планирование или задержки детерминированными.

`timings.jsonl` хранит отдельные измерения: сценарий, номер повтора, логический номер запроса, пул, клиент, фаза, HTTP-статус, исход, задержка в миллисекундах и ID учебной брони. URL, API-ключи и тексты SQL туда не попадают. Время измеряется на клиенте от отправки до разбора HTTP-ответа; прогрев и запуск сервера в него не входят.

`summary.json` содержит версии Python, библиотек и БД, платформу, процессор, число логических CPU, хеш исходников, параметры, исходы и проверки. p50/p95 вычисляются методом ближайшего ранга: отсортированное значение с номером `ceil(p × n)`. Для пустой группы значение — `null`. Задержки создания, повторов, конфликтов и временных отказов разделены.

Ответ `201` сам по себе **не доказывает новую бронь**. Число уникальных фиксаций подтверждается базой. Итоговая сверка проверяет ключи и пользователей, ID броней, нужный пул, состав, цены, авторов аудита и соблюдение вместимости. Неверное сопоставление запроса пулу имеет отдельный проверочный тест.

Стенд завершится с ненулевым кодом при неожиданном исходе, нарушенном инварианте или ошибке выполнения. Несколько запросов могут конкурировать за время процессора и историю бронирований; различие сценариев нельзя причинно объяснять только блокировками.

## Пример фактических измерений

Локальное испытание 02.11.2026: Windows 11, Python 3.12.14, 12 логических CPU, Intel Family 6 Model 186, SQLAlchemy 2.0.55, Uvicorn 0.54.0, FastAPI 0.162.0. SQLite 3.53.1 и PostgreSQL 17.11. По три повтора каждого сценария, 8 клиентов, 200 исходных запросов и 40 повторов успешных ключей.

Во **всех 12 испытаниях** зафиксировано по 96 уникальных броней, 104 ожидаемых конфликта и 40 успешных повторов; нарушений сверки не было. Ниже диапазоны p50/p95 **создания новых броней** между тремя повторами, в миллисекундах:

| База / сценарий | p50, мс | p95, мс |
|---|---:|---:|
| SQLite / общий пул | 10,4–11,9 | 102,1–123,3 |
| SQLite / отдельные пулы | 11,6–17,6 | 540,3–643,2 |
| PostgreSQL / общий пул | 109,7–124,5 | 155,9–179,5 |
| PostgreSQL / отдельные пулы | 110,0–154,3 | 208,3–381,5 |

Это измерения конкретного локального снимка, а не обещание скорости текущей или будущей версии. Снимок имеет SHA-256 `7a8b88ae5409397514947e60bb1a1bfaba172079a1bfddcaa215b1c893a402ce`; последующая проверка границ числовых ID не входила в этот снимок. Полная среда и сырые измерения сохранены локально в `artifacts/load-sqlite-phase3` и `artifacts/load-postgresql-phase3`; они не включены в репозиторий вместе с временными БД. Код стенда позволяет повторить испытание на другом компьютере.

Разброс заметен; из этих данных не следует ускорение от разделения пулов. Рабочая станция не была изолированным измерительным сервером, объём истории на пул различается, а SQLite сериализует записи всей базы. Следующий разумный шаг для оценки производительности — контролируемый стенд и профилирование, а не обещание процентов ускорения.

Независимая проверка дополнительно выполнила шесть PostgreSQL-испытаний и наблюдала 540 операций записи/DDL только в шести собственных схемах. Все они удалены, состояние `public` не изменилось. Исходы, фиксации и ближайшие ранги пересчитаны по сырым записям отдельным кодом.
