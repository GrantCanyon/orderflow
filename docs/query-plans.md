# Почему добавляется индекс состава броней

Исследован неизменённый снимок `25ad49ca74f565a1b8a00c6dcc304bcdfd92e468`.
Это зафиксированный снимок **до maintenance**, а не `851eeda`.
Измерения нельзя приписывать SQL из более позднего коммита. Индекс рассматривается
отдельным патчем; этот отчёт не подменяет проверки такого изменения.
Индекс проверен отдельно на синтетических данных; это не измерение задержки API
в рабочей системе и не обещание универсальной масштабируемости.

**Вывод:** обоснованный кандидат — обычный B-tree
`booking_items(product_id, booking_id, quantity)`. Он переносим между PostgreSQL
и SQLite, позволяет искать состав по позиции и сохраняет результаты SELECT.
Второй индекс таблицы bookings к переносу не рекомендован: проверка обнаружила
ограничение общего плана у partial index и ухудшение календарного плана у status index.
Внедрение индекса — отдельное изменение, не часть этого исследования.

[Компактные результаты, параметры и все три отсчёта](query-plans/results.json) ·
[Полные JSON-планы первого измеренного повтора](query-plans/plans.json).
Время каждого первого плана сверяется с первым отсчётом results, медиана — по трём.

В поставку добавлен [самостоятельный измеритель с генератором](query-plans-reproduce.md).
Он использует сохранённые исторические SQL и схему из указанного коммита, а не
текущие запросы приложения. Независимая проверка сопоставила все сгенерированные
строки и SQL с исходным исследованием. Полный повтор на 30000 броней дал прежний
hash данных, 108 сырых планов и равенство результатов; собственная схема удалена.
Новые времена не заменяют приведённые ниже измерения и не обязаны совпадать с ними.

## Какие запросы проверены

SQL захвачен из выражений `service.py`, условия вручную не переписывались:

- `_segments`: пересечения активных броней для позиции 1, 2–5 января 2030 года.
- `alternatives`: один комплект позиций 1–5, длительность 3 суток, горизонт 20 суток;
  измеряется SELECT, не последующая Python-обработка интервалов и цены.
- `_physical_out`: количество выданного оборудования позиции 1, включая просрочку.

Синтетика: seed 20261102, 300 позиций, 30000 броней, 59894 строки состава,
по 1–3 различные позиции и 1–3 единицы в строке. Из броней 18000 returned,
4500 cancelled, 1500 expired, 3000 confirmed, 1800 hold и 1200 checked_out.
80% завершены; hold включают действующие и истёкшие. Позиции выбирались равномерно.
Фиксированное now — 2030-01-01T08:00:00Z. Все сравнения повторили один hash данных.

Среда: PostgreSQL 17.11 x86_64 Windows, Python 3.12.14. Перед подготовленными
сравнениями — VACUUM ANALYZE своей схемы; кэш прогрет, shared read=0.
Фоновые процессы не отключались, параллельная нагрузка не контролировалась.
Время — серверное Execution Time из EXPLAIN ANALYZE с его накладными расходами,
без передачи результата по сети, Python/HTTP и клиентского интерфейса.

## Исходное избыточное чтение

Первичный ключ состава начинается с booking_id, запрос фильтрует product_id.
Без нового индекса все три SELECT сканировали 59894 строки booking_items.
Для одной позиции выбирались 196 строк, для пяти — 990; календарь возвращал
2 пересечения, alternatives — 140 строк, physical_out — сумму 14.

Первый индекс убирает полный перебор состава. Однако общий physical_out ещё читает
bookings, а alternatives меняется с Hash Join на вложенные циклы с 990 обращениями
к PK bookings. Его shared hits растут 1410 → 3986, хотя на этой выборке время
снижается. Больше обращений к буферам не обязательно означает больше времени
на прогретом небольшом наборе; эффект больших комплектов не проверялся.

## Проверка custom и generic планов

Для реальных выражений выполнены PREPARE/EXECUTE с параметрами, включая product_id,
status, время и элементы IN. Режимы принудительно заданы force_custom_plan и
force_generic_plan; pg_prepared_statements подтвердил нужный тип исполнения.
Один прогрев и три измерения каждого сочетания. Автоматическая подготовка psycopg
отключена только в измерителе, чтобы не конфликтовать с явным PREPARE/DEALLOCATE;
автоматическое переключение драйвера приложения этим не измерялось.
[Описание режимов PostgreSQL](https://www.postgresql.org/docs/17/sql-prepare.html).

В таблице ниже «состав» — первый кандидат с INCLUDE(quantity), без второго
индекса bookings. «partial» и «status» добавлялись к нему отдельно.

| Индексы | Режим | calendar, мс | physical_out, мс | alternatives, мс |
|---|---|---:|---:|---:|
| Исходные | custom | 9.976 | 13.354 | 26.559 |
| Исходные | generic | 9.673 | 16.941 | 62.457 |
| Состав | custom | 1.572 | 6.737 | 5.507 |
| Состав | generic | 1.851 | 6.403 | 6.537 |
| Состав + partial | custom | 1.469 | 0.733 | 7.974 |
| Состав + partial | generic | 1.132 | 8.438 | 7.780 |
| Состав + status | custom | 5.607 | 0.750 | 7.992 |
| Состав + status | generic | 1.203 | 0.792 | 8.416 |

Частичный `bookings(id) WHERE status='checked_out'` даёт 16 shared hits в custom
physical_out. Общий план с `status=$3` его не использует: остаются 795 hits.
Обычный `bookings(status,id)` используется в обоих режимах, в generic — 21 hit.
Но он меняет custom calendar на BitmapOr → Bitmap Heap Scan → Hash Join,
читает все 790 heap-страниц bookings и увеличивает медиану 1.572 → 5.607 мс.
Это не безусловная замена partial index. Второй индекс отклонён как общий патч.

## Переносимый вариант вместо INCLUDE

Следующее отдельное сравнение использует ту же синтетику и оба режима,
но только индекс состава. Сначала INCLUDE, затем обычный ключ из трёх столбцов:

```sql
CREATE INDEX ix_booking_items_product_booking_quantity
ON booking_items (product_id, booking_id, quantity);
```

Это определение кандидата, не команда для самостоятельного изменения рабочей БД.

| Вариант | Режим | calendar, мс | physical_out, мс | alternatives, мс |
|---|---|---:|---:|---:|
| INCLUDE(quantity) | custom | 0.906 | 7.275 | 6.666 |
| INCLUDE(quantity) | generic | 0.987 | 7.884 | 6.787 |
| Три столбца | custom | 1.553 | 7.454 | 6.528 |
| Три столбца | generic | 1.538 | 9.147 | 8.926 |

У вариантов совпали формы планов и shared hits: 789, 795, 3986 соответственно.
В generic-плане явно используется Index Only Scan по переносимому индексу
с product_id=$n. Все результаты совпали. Одинаковая скорость **не доказана**:
некоторые времена переносимого варианта выше, три последовательных повтора
на фоне нагрузки не позволяют отделить свойства индекса от шума/дрейфа среды.
Сравнивать абсолютные времена разных таблиц как единый контролируемый опыт нельзя.

SQLite 3.53.1 отдельно принял это DDL и использовал COVERING INDEX для маленькой
параметризованной выборки из двух строк. Это проверка синтаксиса и доступа,
не замер трёх запросов на SQLite. [Составные и покрывающие индексы SQLite](https://www.sqlite.org/queryplanner.html).

| Индекс | Размер PostgreSQL | Область данных |
|---|---:|---|
| Состав, INCLUDE(quantity) | 4087808 байт (~3.90 МиБ) | Все строки состава |
| Состав, три столбца | 4087808 байт (~3.90 МиБ) | Все строки состава |
| bookings(id), checked_out | 90112 байт (88 КиБ) | 1200 выданных броней |

Обычный status-индекс в 23 раза больше частичного в этом наборе. Все дополнительные
индексы требуют места и обслуживания при изменениях. INSERT/UPDATE, WAL,
блокировки и переходы статуса под нагрузкой здесь не измерялись.

## Проверяемые гарантии и ограничения

Полное сортированное мультимножество результатов (дубликаты сохранены) совпало
во всех 24 сочетаниях prepared-сравнения и 12 сочетаниях переносимого сравнения;
оно также совпало с исходными SELECT без индексов. Дополнительно сохранены SHA256.

Index Only Scan имел Heap Fetches=0 после обслуживания таблиц. Частые изменения
снимают all-visible отметки и могут вернуть чтение heap; этот благоприятный режим
не гарантирован постоянно. [Условия PostgreSQL](https://www.postgresql.org/docs/17/indexes-index-only-scans.html).
Проверен один равномерный набор, одна позиция и комплект из пяти позиций.
Холодный диск, особо популярный товар, большие комплекты, миллион броней,
конкурентные записи и задержки всего API остаются за пределами опыта.

По исходнику availability делает 1 SELECT каталога и 3 SELECT на позицию:
для 300 позиций это 901 запрос. Это подсчёт по коду, не измеренное время экрана.
Индекс не уменьшает число обращений; такой полный сценарий требует отдельной проверки.

Все испытания выполнялись в собственных test_UUID схемах тестовой базы.
Перед удалением проверены владелец и уникальная метка, отсутствие схем затем
подтверждено. public и исходники приложения не изменялись. JSON не содержит
строк подключения, локальных путей, исходных пользовательских данных или URL.

## Внедрение после исследования

В актуальном приложении выбран ровно один переносимый индекс: `booking_items(product_id, booking_id, quantity)`. Он создаётся вместе с новой таблицей; существующая база получает его только по явной команде `orderflow create-indexes`. [Инструкция обновления и границы блокировок](operations.md#явное-обновление-индекса-существующей-базы).

Интеграция проверена отдельно от исторического опыта: текущие 116 тестов покрывают SQLite и PostgreSQL, включая новую базу, повтор команды, сохранение строк и аудита и отсутствие фонового DDL при запуске существующей базы. Независимая проверка также подтвердила отказ по реальному таймауту блокировки PostgreSQL без частичного индекса и успешный повтор после её снятия. Ограничения зависимостей проверены установкой в новое окружение.

Эти проверки подтверждают корректность внедрения, но не измеряют заново планы SQL после добавления обслуживания. Исторические результаты выше относятся только к снимку `25ad49c`; они не являются замером текущего UNION ALL с обслуживанием или обещанием ускорения API. Публичные JSON и методика позволяют проверить выводы, но локальный генератор и измеритель не поставляются, поэтому точная независимая репродукция набора остаётся ограниченной.
