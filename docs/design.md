# Домен и архитектура OrderFlow

## Зачем эта система

Пункт проката продаёт возможность использовать оборудование в определённое время. Остаток «12 колонок» недостаточен: нужны интервалы, состав комплекта, срок удержания и физический возврат. PostgreSQL — основная база для конкурентной работы. SQLite — честно обозначенный локальный демонстрационный режим.

## Контракт

- Позиция каталога — пул взаимозаменяемых единиц. Бронирование содержит до 50 разных позиций и создаётся атомарно.
- Все даты имеют часовой пояс и нормализуются в UTC. Интервалы полуоткрытые: `[начало, конец)`. В точке окончания ресурс доступен следующей брони.
- Доступность определяется максимумом одновременной загрузки. Две последовательные брони не суммируются, даже если обе пересекают длинный проверяемый период.
- Стоимость: количество × сохранённая ставка × число начатых 24-часовых суток. Цена и итог хранятся целыми копейками в `BIGINT`; итог ограничен `2^53−1`, чтобы оставаться точным числом в JSON/JavaScript.
- По умолчанию резерв живёт 15 минут; допустимый TTL — от 1 до 60 минут. При `now >= expires_at` он уже не занимает ресурс и не подтверждается, даже если физический статус ещё `hold`.
- Состояния: `hold → confirmed → checked_out → returned`; из `hold` и `confirmed` допустима отмена. Истёкший резерв имеет эффективный статус `expired`.
- Выдача возможна только при `start_at <= now < end_at`. Перенос разрешён только до выдачи; срок резерва при переносе не продлевается. Начало переноса перепроверяется после ожидания блокировок.
- Ранний возврат освобождает ресурс, но не пересчитывает стоимость. Возврат только целиком.
- Уже выданные единицы учитываются в физическом остатке независимо от окончания планового интервала. Выдача и уменьшение парка не могут сделать физический остаток отрицательным.
- Успешное изменение и аудит фиксируются одной транзакцией. Неудачные операции не оставляют бизнес-события; журнал отказов безопасности — отдельная будущая задача.

## Порядок блокировок

Все изменения, влияющие на ресурс, сначала блокируют позиции каталога по возрастанию `product_id`. Затем при необходимости блокируют само бронирование. Состав позиций после создания неизменяем, поэтому его можно прочитать для выбора блокировок заранее.

PostgreSQL использует `SELECT … ORDER BY id FOR UPDATE` на уровне `READ COMMITTED`. После ожидания следующий запрос видит уже зафиксированные изменения конкурента. SQLite начинает записывающую транзакцию через `BEGIN IMMEDIATE`: проще, но все записи сериализуются в масштабе базы.

Создание, перенос, подтверждение, отмена, выдача, возврат, уменьшение парка и пакетное завершение резервов придерживаются одного порядка. Пакетное завершение сначала блокирует объединение всех затронутых пулов; оно не удерживает первый пул в ожидании меньшего номера из следующего бронирования.

Внутри транзакций нет сетевых вызовов. Проверка доступности на чтение не обещает фиксацию ресурса: бронирование повторно проверяет её под блокировками.

## Как работает временная шкала

Для каждого пересекающегося активного бронирования создаются два события: `+quantity` на начале и `−quantity` на конце. Интервал обрезается границами запроса. События в одинаковой точке применяются вместе, затем строится следующий сегмент с текущей загрузкой и списком бронирований.

Например, при парке из трёх колонок:

```text
10:00          12:00          14:00
Бронь A: 2 ──────┘
Бронь B:                2 ──────┘
Новая:   1 ─────────────────────┘
Итого:   3              3
```

Новая бронь допустима. Сложение всех пересекающихся количеств дало бы ошибочные пять.

## Идемпотентность

Ключ связан с устойчивым ID аутентифицированного пользователя, а не с его отображаемым именем. Перед хешированием даты переводятся в UTC, позиции сортируются по ID, текст очищается от краевых пробелов, а TTL по умолчанию включается явно. Повтор эквивалентного запроса возвращает ту же бронь с её текущим состоянием. Другое содержимое с тем же ключом — `idempotency_conflict`.

Проверка повторяется после блокировок. Уникальная пара `(principal, key)` в БД закрывает случай, когда два запроса имеют одинаковый ключ, но блокируют разные пулы. Проигравшая транзакция откатывается целиком; затем результат победителя сравнивается с запросом. Отказ по доступности не расходует ключ.

Конфигурация каждого ключа содержит обязательные `id`, `name`, `role`. Разные пользователи могут иметь одинаковое имя, но должны иметь разные ID. Несколько ключей одного ID намеренно разделяют область идемпотентности для ротации. Переименование не меняет идентичность. Бронирование и аудит хранят ID и снимок отображаемого имени на момент действия.

## Модель данных

| Таблица | Назначение |
|---|---|
| `products` | Артикул, название, категория, размер парка и текущая ставка |
| `bookings` | Период, статус, TTL, автор, ссылка и итог |
| `booking_items` | Количество и сохранённая ставка каждой позиции |
| `idempotency` | Пользователь, ключ, хеш нормализованного запроса и бронь |
| `audit` | Монотонный номер, автор, действие, детали и время |

Положительные количества, допустимые статусы, порядок границ, неотрицательные деньги и уникальность ключей закреплены SQL-ограничениями. Приложение добавляет верхние границы, роли, разрешённые переходы и правила ресурса.

## Почему один сервис

Доступность, запись брони и аудит требуют общей атомарной границы. Один процесс приложения и одна транзакционная база дают её без распределённых блокировок и компенсаций. Микросервисы здесь повысили бы сложность без доказанной пользы.

Интерфейс написан на браузерных модулях: для форм, таблиц, диалогов и шкалы не нужна сборочная цепочка. Все ресурсы локальные. Пользовательский текст вставляется через `textContent`; нет исполнения HTML из названий. CSP ограничивает источники текущим сервером. Встроенные CDN-страницы Swagger/ReDoc отключены; контракт доступен как `/openapi.json` и в локальной инструкции.

## Сознательные ограничения

Одна организация, полный возврат, отсутствие серийных номеров, ремонта, буферов подготовки и реальных платежей. Просроченные единицы не занимают все будущие интервалы автоматически: они видны на шкале физического остатка и блокируют невозможную выдачу. Администратор БД находится вне модели защиты аудита: приложение не предлагает изменение или удаление записей, но владелец БД технически может менять таблицы.

Чтения каталога и шкалы не являются единым блокирующим снимком. Для большого парка нужны индексы, анализ планов и сокращение числа запросов; текущая версия ориентирована на небольшой пункт проката. Система не заявляет результаты нагрузочного тестирования.

## Альтернативные периоды

Поиск для новой брони читает каталог, актуальные ставки и необходимые бронирования одним SQL-оператором. Он объединяет непригодные интервалы всех позиций и выбирает по самому раннему началу каждого максимального свободного участка. Временной сетки нет; длительность передаётся целым числом микросекунд. Предложения не записывают и не блокируют ресурс, а их цена и доступность проверяются снова при обычном создании. Подробный контракт находится в [описании альтернатив](alternatives.md).
